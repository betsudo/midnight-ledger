The current-branch baseline is published as [PR #33](https://github.com/betsudo/midnight-ledger/pull/33), stacked on the plain upstream sync [PR #31](https://github.com/betsudo/midnight-ledger/pull/31). The optimized 0.8.4 candidate in PR #32 is a separate, wire-incompatible line. It does not change Ledger8. Recheck upstream heads before merging.

## Baseline gates and remaining work

- A Compact 0.36.1 generated ZKIR 3.1 counter circuit passed v3 keygen, heap and mapped proof, verification, and forced spill on both Ledger9 lines. The current line also has an ignored `k=15`, 32,185-row hash-chain probe with reproducible commands and single-run timing in `proof-server/tests/compact-v3-hash-chain/README.md`. The pinned proof features include native `mmap` and `disk-spill`; the external v3 wasm package was checked without those features.
- The current line passed all eight proof-server library tests, including concurrent queue admission, and the v3 test target (three passing, one ignored). The V2 `/k` endpoint passed. The local V2 minimal prove/verify and wrong-statement rejection tests passed using a SHA-256-verified `k=4` public parameter; their temporary target and parameter file were removed.
- The current proof-server admits at most two concurrent request bodies by default, caps each at 512 MiB, and gives each body 120 seconds to arrive. `/prove`, `/check`, and `/prove-tx` reject a full job queue before reading the body; `/k` shares the ingress cap. A declared or streamed body over the cap receives 413; excess ingress or a full job queue receives 429; a slow body receives 408. The server CLI exposes all three ingress limits. The `/prove` key is shared through an `Arc` until the resolver actually requests an owned copy; the resolver API can still clone on use. Five focused `/prove` rejection tests, including full-queue and declared/chunked oversize cases, six `/k`/`/check` rejection tests, and eight library tests passed locally. This mitigates #13; large-key burst memory evidence and a policy for deliberately unlimited (`job_capacity=0`) queues remain open.
- At the PR #33 baseline, the HTTP V2 transaction proof test still required generated `fallible` key fixtures under `MIDNIGHT_LEDGER_TEST_STATIC_DIR`; the minimal V2 test did not qualify it. The two transaction-body rejection tests requiring that fixture likewise could not run; the three fixture-free rejection tests passed. PRs #34–#36 subsequently added V3 request context, HTTP cancellation and request-owned key loading. Released Ledger 9.1.0.1 V2 and V3 serialized IR, key, VK and proof fixtures now pass focused compatibility tests under heap and mapped parameters, with forced spill selected. PK disk-cache identity (#14) and cross-line proof parity (#26) remain open.
- The current v3 benchmark verified both proofs, but they were not byte-identical under the seeded test RNG. Verification, rather than byte equality, is its correctness gate. A separate forced-spill run observed about 997 MiB peak RSS for the whole test process and at most 40 MiB of anonymous mapped spill files alive together, sampled with `lsof`; see the fixture README for the method and limits. These observations do not isolate per-arm memory or establish throughput.
- The current-branch baseline is published as PR #33, with follow-ups #34–#36. Exact-head CI and external review are required before merge. The separate stable-tag line remains local. Remote PRs #15/#16 and the old `ledger-9-patched` head were not moved. The two dirty Claude worktrees and preexisting untracked proof fixtures remain untouched. All disposable build targets from completed local iterations were removed.

## External ZKIR v3 request-context boundary

The PR #33 baseline resolves registry `midnight-zkir` 3.2.1. Its `IrSource` implementation of `transient_crypto::proofs::Zkir::prove` calls `midnight_zk_stdlib::prove` with parameters, key, circuit, public inputs, witness and RNG, but no proof context. The baseline `Zkir` trait and `ProofPreimage::prove` likewise have no policy or cancel-token argument. Consequently that provider can select mapped parameters and the process-wide compatibility policy can force coset spill, but neither proves request-scoped spill selection or cancellation isolation for v3. The earlier Compact v3 proof tests establish the former behavior only.

A disposable `midnight-proof-server` example checked the actual v3 dependency graph by calling `ProofPreimage::prove::<zkir_v3::IrSource>(rng, params, resolver, &context)` with a `ProverContext`. `cargo check -p midnight-proof-server --example zkir3_context_probe` reached the proof server and failed with `E0061`: the method takes three arguments and the context is an unexpected fourth argument. The compiler located the method at local `transient-crypto/src/proofs.rs:1427`. The example, its 701 MiB target, and its temporary worktree were removed after this expected failure.

The follow-up extends the `transient-crypto` call boundary, the forked `midnight-zkir` 3.2.1 implementation, and the forked released-source stdlib 2.4.0 with additive `prove_with_context` entry points. The old `prove` signatures remain. The proof server passes a fresh context with the configured process memory policy to V3; V0/V1/V2 stay on their existing routes. The Compact-generated V3 counter passes keygen, heap and mapped proof, verification, and a pre-cancelled context check on this exact dependency graph; a focused forced-spill invocation also passes. The low-level mmap/spill storage remains only in `midnight-proofs`.

PR #34 creates this context **without an HTTP request cancellation token**. In this follow-up, `/prove` gives V3 each request its own token and cancels its pending job when its handler drops. Worker claim and pending cancellation compete under one lock, and cancelling a queued job releases its captured body. A job deadline cancels that request. The default HTTP/1 half-close behavior is preserved for existing clients; operators can opt into handler abort on client write-side close with `--abort-half-closed-clients`. Thus a peer close is only a reliable cancellation trigger under that transport setting. V0/V1/V2 proof execution and transaction proving still use their compatibility paths.

The HTTP cancellation follow-up passed 16 proof-server library tests, 32 proof-server integration tests with the Ledger8.1 fixture directory, and a real HTTP Compact-generated V3 mapped-parameter prove/verify test. The HTTP test queues a request, closes its client, checks that the pending job disappears, then proves and verifies a new request. It also passed with the process spill policy selected at the circuit's `k`. This small circuit does not establish that spill bytes were written.

This key-policy follow-up adds `ProverKey::init_with_context`, a policy-keyed cache with one retained entry, serialized cache misses, and cancellation checks while waiting for the build gate or a per-key lock. The external ZKIR V3 source at `3c4e2a6a` calls that loader and forwards the same policy through stdlib's `MidnightPK::read_with_policy`; context-free proving retains its old process-policy path. A directly generated V3 key records the keygen process policy: it can prove under the matching policy without mapped key storage, while a mapped-key request requires a serialized reload and fails explicitly. On the previous `e1e93357` graph, the transient-crypto library passed 79 tests and ZKIR passed 53 library tests. On that graph, the V3 HTTP context test, five active mapped-parameter tests including direct keygen policy, the concurrent policy-cache test, and 32 proof-server integration tests passed. A forced-spill Compact-generated V3 hash-chain test at `k=15` and 32,185 rows also proved and verified with heap and mapped parameters (`MIDNIGHT_BENCH_REQUIRE_SPILL=1`); its single local run is a functional gate, not a reproducible benchmark. The released V2/V3 fixture tests now verify and reprove against Ledger 9.1.0.1 artifacts with heap and mapped parameters; both reject truncated key/proof bytes and a mismatched public statement. A repeatable, separate-process `k=4` V2/V3 heap-versus-mapped smoke baseline is recorded in [release-policy-smoke.md](../proof-server/tests/release-policy-smoke.md). It confirms policy function and observed spill bytes at a small circuit size, but cannot establish high-`k` memory savings. The `6b71786d` / `3c4e2a6a` graph still requires fresh exact-head CI and integration checks. A low-level key read already in progress cannot be interrupted mid-read. Before a release-compatible completion claim, retain an explicit high-`k` key-load/memory gate and a same-circuit memory/latency/spill-disk comparison. Keep #30, #13, #14 and #26 as the existing owners of the adjacent work. The separate 0.8.4/3.3.0 candidate remains isolated.
